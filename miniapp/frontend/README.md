# Клиент Arti Mini App

React + TypeScript + Vite; интерфейс принятой концепции 04 «Левая рука» (`mockup/README.md`). MA04 подключает отправку текстовых сообщений Арти и общую историю с Telegram к серверной сессии MA01. Функции включаются только по серверным capabilities; локальный просмотр остаётся без отправки и ответов. Социальные чаты, вложения и генерации ещё недоступны и обозначены в интерфейсе явно. Примерные переписки и воспоминания из макета не используются.

```powershell
npm.cmd ci
npm.cmd run lint
npm.cmd run typecheck
npm.cmd test
npm.cmd run build
```

Требуется Node.js 22.12+ (или совместимая поддерживаемая версия). Проверено на Node.js 24.15.0. Версии зависимостей зафиксированы в package-lock.json. Сборка `dist/` имеет base `/static/app/`; aiohttp отдаёт её index на `/`, ассеты на `/static/app/assets/`. Клиент и API в production находятся на одном origin. Для разработки `npm.cmd run dev` запускает Vite на loopback с прокси API на 127.0.0.1:8765; cookie/origin необходимо учитывать при проверке аутентификации, итоговую проверку проводить на общем origin через сервер.

Telegram SDK загружается с официального telegram.org. Шрифты (Cormorant Garamond, Onest, IBM Plex Mono, Caveat через `@fontsource`, только cyrillic+latin и используемые веса) и портрет находятся в собственной сборке, внешних шрифтов и изображений нет. Портрет — `mockup/assets/arti-portrait-v4.webp`, облегчённая копия сгенерированного ранее для макета `arti-portrait-v2.png`.

Сервер проверяет initData и выдаёт HttpOnly session cookie; клиент держит CSRF только в памяти. Ни сессия, ни initData не записываются в localStorage/URL/логи. В localStorage сохраняется только тема. Без Telegram пользователь получает объяснение, как открыть приложение; локальный просмотр доступен только после явного нажатия и только при `healthz.mode=demo`. Ошибка Telegram-входа никогда не включает деморежим.

Тема `system` («Как в Telegram») следует Telegram `themeChanged` либо настройкам браузера; `light` — день «бумага», `dark` — вечер «лампа». Состояние набора текста Арти («сейчас прочитает…», «подбирает слово…») берётся только из `request_state` в истории и live events, без таймеров. Реакции и маркер «написала первой» отрисовываются только при наличии этих полей в сообщении; API их пока не отдаёт (MA07, MA10). Полоса «Сейчас у Арти», Комната Арти и настройка «Не упоминать» в Профиле (`src/ArtiLife.tsx`, `src/life.ts`) включаются capability `arti_life` и подписывают образ, настоящее чтение и настроение раздельно (H6 P2). SDK BackButton, viewport и safe-area события подключаются с cleanup. Семантические кнопки/навигация, нативный modal dialog, состояния загрузки/ошибки/пустых данных и поддержка reduced-motion включены. Реальные мобильные клиенты Telegram требуют отдельной проверки, браузерный запуск её не заменяет.

Отправка использует UUID намерения и точное тело запроса, включая обязательную `history_revision` из текущей истории. До получения ревизии отправка отключена. При неопределённом результате UUID и исходная ревизия сохраняются для явного повтора; старый текст не переносится на новую ревизию после сброса, новая генерация автоматически не запускается. Ответ `409 history_reset` немедленно очищает попытку и запускает чтение актуальной истории. Подтверждение через поток также снимает неопределённость отправки. Текст сообщений, попытки и история хранятся только в памяти вкладки; HTML из ответов не исполняется. Вложения остаются отключены.

Обновления приходят через cookie-authenticated SSE с курсором беседы. При обрыве клиент закрывает соединение и использует polling с ограниченным интервалом 3,5–15 секунд, периодически пробуя SSE снова. Отдельные HTTP команды несут CSRF; токены и initData не попадают в URL потока. Скрытие вкладки, уход со страницы, выход и отзыв доступа прекращают подписки и незавершённые чтения. Истечение сессии закрывает приватный интерфейс. Изменение `history_revision` очищает старую историю, черновик и неподтверждённую попытку до повторного чтения; стёртое сообщение автоматически не отправляется.

История читается страницами по 50 сообщений. Replay событий не подгружает более старые страницы самовольно. Загрузка предыдущей страницы сохраняет позицию чтения; новые ответы прокручиваются вниз только рядом с концом истории или при собственной отправке. В остальных случаях появляется кнопка «Новые сообщения». Список чатов тоже получает обновления, без второго потока для уже открытой беседы. Очередь и ответ отображаются по действительным состояниям серверного задания.

Для проверки ошибок протокола есть отдельный **тестовый** сервер, который не использует Telegram, базу данных или AI-провайдеров и слушает только `127.0.0.1:8779`:

```powershell
npm.cmd run build
$env:ARTI_FRONTEND_PROTOCOL_FIXTURE='1'
npm.cmd run test:ui:serve
```

Это fixture из `tests/protocol-server.mjs`, не production backend и не режим приложения. Она намеренно содержит подписанные как тестовые сообщения. `POST /__fixture` управляет сценариями: `mode` (`normal`, `queued`, `polling`, `offline`, `lost-ack`, `invalid-ack-offline`, `reject`), `postDelay`, `reset`, `expired`, `revoked`, `telegramText`, `artiText`, `requestState`, а для «Жизни Арти» — `lifeReset` (настройка по умолчанию) и `lifeMood` (объект или `null`). Данные жизни в fixture синтетические, ссылки ведут на example.org. `GET /__fixture` показывает UUID и тела только тестовых отправок для проверки дедупликации. Остановка и повторный запуск восстанавливают исходную тестовую историю. Отдельная проверка реального API с изолированной PostgreSQL и fake provider проводится на стороне серверных тестов.
