# MA03–MA04 · техническое решение

Утверждённый пакет: настоящий текстовый ответ Арти внутри Mini App и общая личная история с ботом. Реализация использует существующий `process_user_reply`, cognition и durable text workers; второй AI-процессор не создаётся.

1. **Источник и очередь.** Явные channel/source_key в scope/request, message_id=None для Mini App. Подлинный private chat ID пользователя остаётся адресом общего контекста/FIFO. Нейтральная регистрация когнитивного источника, app message/event/outbox и принятого задания фиксируется одной транзакцией. Helpers получают optional conn; старый codec v1 и Telegram payloads читаются без изменений смысла. Для app coalescing отключён.
2. **Порядок блокировок.** Когнитивные контексты → материалы → app conversation → request lane → request row → publication rows. В `RequestStore.enqueue` dependency locks переносятся перед lane lock: иначе атомарный app intake образует инверсию с Telegram enqueue. Intake дополнительно берёт существующий organizer-cognitive-routing fence до контекста, как cognitive delivery authority guard. Transaction-aware helpers повторно используют conn, включая pending organizer lookup, и не исчерпывают pool вложенным acquire при конкурентном intake. Provider/network I/O вне транзакций.
3. **Обработка.** Тот же текстовый pipeline, persona, память, выбор модели, intent/search и очистка ответа. Выход Mini App — явный text sink с UUID публикации. Нативные сообщения/receipts не выдаются за Telegram Message. Telegram-only reactions/voice/stickers/media cards не выполняются без соответствующей capability; подключение медиа остаётся MA07–MA08. Органайзер использует существующий domain API со стабильным source key.
4. **Публикация.** Отдельный атомарный native publication receipt `(request_id,ordinal)` сохраняет app reply, cognitive delivered_action, зависимости, encode job и event/outbox. Перед commit проверяются lease/deadline, epoch/source/support/memory и владелец беседы. После commit восстанавливается тот же UUID. Telegram mirror — отдельная долговечная доставка уже опубликованного текста; timeout влияет только на mirror и не вызывает повторной генерации/когнитивного действия.
5. **История.** App transcript — проекция разрешённых cognitive user/delivered_action событий private/default/topic -1 с реальным владельцем. Перенос исторических записей идемпотентен, в порядке времени/ID до нового intake; сохраняется source mapping, не запускаются interpretation/generation. Живые Telegram события дочитываются reconciler; проверяются неотображённые source IDs, а не ненадёжный глобальный max cursor. Read API повторно проверяет source/reset/rebuilding; suppression/reset также стирает текст проекции и отменяет доставку.
6. **Обновления UI.** POST отправляет client UUID и history_revision; revision сравнивается под блокировкой даже при пустом reset, старый запрос не становится новым. SSE с seq внутри конкретной беседы, heartbeat и проверкой сессии/прав. Reconnect и polling используют тот же cursor/visibility API. Статусы — принято/очередь/обработка/ошибка, неизвестное зеркало не скрывает готовый ответ. Composer поддерживает явный повтор с тем же UUID/телом/revision без дублей. Mirror metadata повторно публикует resource ID без создания второго сообщения.
7. **Нативные комнаты.** Отдельная UUID-идентичность когнитивного контекста с явной сериализацией, без фиктивного chat ID и изменения старой identity/hash. В этом пакете проверяются allocation/round-trip; исполнение групповой Арти остаётся закрытым до MA06.

Критические файлы: `cognition/{types,serialization,runtime,repositories,jobs,delivery}.py`, новые аддитивные миграции; `bot/{queue,request_runtime,request_store,request_codec,organizer_commands}.py`; `conversations/` intake/history/publication/mirror; `miniapp/server.py`, `miniapp/frontend/`.

Проверки: одинаковый POST и изменённый payload, атомарный rollback, общий FIFO Telegram/app, reset до worker, удаление во время генерации, stale lease, crash до/после native commit, неизвестная mirror-доставка, старый codec, >100 событий/одинаковое время/повтор импорта, SSE reconnect/erase/logout. Одноразовые БД и fake providers/Telegram; реальный бот/рабочая БД не используются для тестов. Клиент проходит typecheck/lint/tests/build и независимую browser-проверку. Живой HTTPS/Telegram deployment относится к отдельному этапу.
