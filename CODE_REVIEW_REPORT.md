## 1. Executive summary

Проект функционально богатый и местами зрелый: параметризованный SQL, SSRF-guard с резолвингом всех IP, fencing `<user_memory>` против prompt-injection, fail-closed парсер эмоциональной интроспекции, `FOR UPDATE`-транзакции в аффективных методах, атомарный захват слота проактивного пуша, аудит-лог `/vclone`. Базовая гигиена после первого аудита заметно выросла.

**Тем не менее, к продакшен-релизу проект сейчас не готов.** Блокеры и главные риски:

1. **Бот не стартует с чистой установки** — `requirements.txt` не содержит `beautifulsoup4`, который импортируется на уровне модуля в цепочке `main.py → bot/handlers.py → ai/tts.py`. Также отсутствуют `yt-dlp`, `pydub`, `gradio_client` и extra `python-telegram-bot[job-queue]` (без него анти-спам блокировка падает с `AttributeError`). Работает только на машине разработчика, где пакеты ставились вручную (DEP-01).
2. **Дедлок пула БД под нагрузкой**: `ChatEmotionalState.update_state` держит транзакцию с `FOR UPDATE` и внутри неё берёт **второе** соединение из пула (`infer_user_timezone`). Семафор разрешает 10 параллельных текстовых ответов при пуле `max_size=10` — классический самодедлок, останавливающий всю работу с БД (RACE-01).
3. **Дыры в разграничении доступа**: голосовые сообщения обрабатываются (скачивание + STT + LLM + ответ) даже в чатах, где бот выключен `/stop`, и без rate-limit (AUTH-01); проактивный шедулер пишет в выключенные чаты (AUTH-02); реакции на **любые** сообщения (не только бота) накручивают «близость», открывая проактивные пуши (AUTH-03).
4. **Целостность памяти**: консолидация неатомарна и умеет терять/дублировать факты (MEM-01); перестроение профиля затирает параллельные обновления близости (MEM-02); в группах профиль пользователя собирается из чужих данных (MEM-03); тексты-заглушки об ошибках LLM сохраняются в память как нормальные ответы (MEM-06).
5. **Мёртвый функционал в дефолтной конфигурации**: `TTS_ENABLED = False` глушит `/vclone`, `/steal`, `/dub`, `/voice_save` — тысячи строк кода недостижимы, хотя команды заявлены в меню (CONF-01). `/cancel` не отменяет генерации — функции отмены никогда не вызываются (REL-03).
6. **Гонка с потерей сообщений** в per-user очереди текстовых ответов (RACE-02).

### RACE-01 (High). Дедлок пула соединений: второе соединение внутри `FOR UPDATE`-транзакции

**Файлы:** `database/models.py:1728-1752`, `:1590-1605`; `database/connection.py:51-52`; `bot/queue.py:104`.

```python
# database/models.py — update_state
async with get_db() as conn:
    async with conn.transaction():
        state = await conn.fetchrow("SELECT ... FROM chat_emotional_states WHERE chat_id=$1 FOR UPDATE", chat_id)
        ...
        user_tz = state["user_tz"]
        if user_tz is None and user_id is not None:
            user_tz = await infer_user_timezone(chat_id, user_id)   # ← внутри транзакции
```

`infer_user_timezone` (`models.py:1590-1605`) вызывает `UserLocation.get` и собственный `async with get_db()` — то есть **берёт второе соединение из пула, не отпуская первое**, прямо внутри открытой транзакции с блокировкой строки.

**Почему это проблема.** Пул — `min_size=2, max_size=10` (`connection.py:51-52`); семафор текстовых ответов — 10 одновременных (`queue.py:104`), каждый вызывает `update_state` (`queue.py:733`). Если ~10 корутин одновременно вошли в `update_state` и всем нужен `infer_user_timezone` (типично после рестарта/для новых чатов, где `user_tz IS NULL`), все 10 соединений заняты внешними транзакциями, и каждая ждёт второе соединение, которое никто не может освободить. Полная остановка работы с БД до `command_timeout` (60 с) и каскад ошибок — ровно в момент пиковой нагрузки.

### RACE-02 (High). Потеря сообщений в per-user текстовой очереди

**Файл:** `bot/queue.py:486-505, 572-574`.

```python

    request = await queue.get()
    ...
_user_queues.pop(user_id, None)   # (2) самоликвидация
_user_workers.pop(user_id, None)

# продюсер enqueue_reply
```

### MEM-01 (High). Консолидация памяти неатомарна и искажает provenance

**Файл:** `memory/consolidator.py:204-255`.

```python

    ... await MemoryWikiPage.save(...)        # 1) wiki пишется сразу
```

### MEM-02 (High). Lost-update аффективного блока профиля

**Файл:** `memory/profiles.py:148-177`; `database/models.py:1262-1330`.

### MEM-03 (High). Кросс-пользовательское загрязнение профилей в группах

## 4. Детали: Medium

### Память, консолидация, профили

#### MEM-04. Триггер автоконсолидации по глобальному счётчику
**Файл:** `memory/storage.py:412-417`

```python
if (MEMORY_CONSOLIDATION_AUTO and source_message_id
        and MEMORY_CONSOLIDATION_INTERVAL > 0
        and source_message_id % MEMORY_CONSOLIDATION_INTERVAL == 0):
    consolidation_task = asyncio.create_task(maybe_consolidate(chat_id=chat_id, ...))
```
`source_message_id` — глобальный `BIGSERIAL` из `memory_messages`, общий для всех чатов. Условие `% 50 == 0` срабатывает у ~2% сохранений независимо от чата: консолидируется тот чат, чьё сообщение «случайно» получило кратный 50 id. Активный чат может систематически «перепрыгивать» кратные id, тихий — внезапно консолидироваться. Частота обслуживания чата не должна зависеть от трафика соседних чатов.
**Рекомендация:** счётчик/таймер per (chat_id, mode): например, число активных фактов с последней консолидации.

#### MEM-05. Дубли таймлайна из-за допущения о сортировке массива
**Файлы:** `database/models.py:1422-1431`; `memory/timeline.py:77-87`

```sql
SELECT COALESCE(MAX(source_message_ids[array_length(source_message_ids, 1)]), 0) ...
```
Берётся **последний элемент** массива `source_message_ids`. Но `_normalize_events` сохраняет id в порядке, который вернула LLM, не сортируя. Если последний элемент не максимален, `after_id` следующего прохода занижен → сообщения переобрабатываются и события дублируются (уникальных ограничений в `memory_timelines` нет). Аналогичное допущение в `MemoryChunk.latest_message_id` (`models.py:614-621`) безопасно только пока чанкер сортирует id.
**Рекомендация:** сортировать `source_ids` при нормализации и/или считать `MAX(unnest(source_message_ids))` в SQL.

#### MEM-06. Тексты-заглушки об ошибках сохраняются в историю и память
**Файлы:** `ai/generation.py:500, 645`; `bot/queue.py:1016-1023, 1103-1114`

`generate_response_stream` при сбое возвращает обычной строкой «К сожалению, модель … недоступна» / «К сожалению, произошла ошибка. Попробуйте позже.». Вызывающий код неотличимо сохраняет это в `chat_history` и отправляет в `remember_exchange` → LLM-экстрактор добросовестно превращает сообщение об ошибке в summary/чанк, а заглушка попадает в контекст следующих ответов. Память постепенно засоряется «Арти говорила, что у неё ошибка».
**Рекомендация:** возвращать признак ошибки отдельно (исключение или флаг); при ошибке не сохранять обмен в историю/память.

#### MEM-07. Дедупликация фактов и чанков подвержена гонке
**Файл:** `database/models.py:798-810` (`MemoryFact.create`), `:515-523` (`MemoryChunk.create`)

Проверка дубликата — SELECT по `lower(fact_text)` / по равенству массива `message_ids`, затем INSERT. Транзакция не защищает от phantom-вставки конкурента; уникальных индексов нет. Параллельные `remember_exchange` (две беседы одного чата) или backfill + живой бот создают дубли. Для чанков дедуп к тому же срабатывает только при точном совпадении массива id — смена `--batch-size` в `backfill_memory_chunks.py` плодит контентные дубликаты (M-10 прошлого аудита — открыт).
**Рекомендация:** уникальные индексы (`(chat_id, mode, md5(lower(fact_text)))`; хеш содержимого чанка) + `ON CONFLICT DO NOTHING RETURNING id`.

### База данных, согласованность

#### DB-01. SQL через `%`-форматирование в `get_with_ttl`
**Файл:** `database/models.py:305-312`

```python
row = await conn.fetchrow("""
    SELECT ... WHERE user_id = $1 AND updated_at > NOW() - INTERVAL '%s seconds'
""" % ttl_seconds, user_id)
```
Единственное место в проекте, где значение интерполируется в SQL строкой. Сейчас `ttl_seconds` — int из кода, не из ввода, но это мина: первый же вызов с нечисловым/внешним значением станет инъекцией.

#### DB-02. Гонки инициализации
**Файлы:** `database/connection.py:21-27, 693-702`; `database/models.py:1738-1743`

- `get_db()` при `_pool is None` вызывает `init_db()`; сам `init_db` защищён лишь `if _pool is not None: return` без `asyncio.Lock` — две конкурентные корутины на старте создадут два пула (один утечёт).
- `update_state`: при отсутствии строки выполняется обычный `INSERT` без `ON CONFLICT` — два первых сообщения в новый чат одновременно дадут `UniqueViolation` и ошибку обработчика (рядом в `get_or_create`, `:1709-1721`, `ON CONFLICT` есть).

**Рекомендация:** `asyncio.Lock` вокруг инициализации пула; `INSERT … ON CONFLICT (chat_id) DO NOTHING` + повторный `SELECT … FOR UPDATE`.

#### DB-03. Смесь наивного времени, времени БД и целочисленных TZ-офсетов
**Файлы:** `database/models.py:33, 1894`; `ai/generation.py:68`; `bot/queue.py:628, 1994`; `utils/chat_history.py:43`; `database/models.py:1592, 1611-1620`

`ChatHistory.save` пишет `datetime.now()` приложения, `created_at` — `NOW()` БД; циркадная логика и шедулеры используют устаревший `datetime.utcnow()` (deprecated в 3.12+) с целочисленным `user_tz` (в т.ч. выведенным из долготы `int(round(lng/15))` — без DST и политических зон); `infer_user_timezone` вычитает локальный офсет сервера из наивных таймстампов БД. Хорошая práctica уже есть точечно (дельты в `update_state`/`mark_used` считаются на стороне БД — M-07 закрыт), но вокруг неё остаётся зоопарк: ошибки «±1-2 часа» в quiet hours проактива и резолве «завтра» неизбежны при смене TZ сервера/переезде.
**Рекомендация:** хранить и сравнивать всё в UTC (`TIMESTAMPTZ`), для локального времени пользователя использовать `zoneinfo`; заменить `utcnow()` на `datetime.now(timezone.utc)`.

### Устойчивость и производительность

#### REL-01. Один медиа-воркер на все чаты + длинные паузы
**Файл:** `bot/queue.py:425-453` (воркер и cooldown), `:184-222` (ретраи image)

`generation_worker` обрабатывает image/video/music строго последовательно; после **каждой** музыкальной задачи спит `MUSIC_COOLDOWN=120` с (`:451-453`), ретраи image — до 5 попыток с бэкоффом 10→160 с. Один пользователь, заказавший музыку, на 2+ минуты блокирует генерацию картинок всем чатам; деградация API превращает очередь в пробку на десятки минут.
**Рекомендация:** отдельные очереди/воркеры по типам; cooldown — на музыкальный API-клиент, а не на общий воркер; дедлайны на задачу.

#### REL-02. +5 секунд латентности каждому текстовому ответу
**Файл:** `bot/queue.py:507-525`

Rolling-debounce: после `queue.get()` воркер всегда ждёт до 5 с новых сообщений, т.е. каждый одиночный вопрос получает +5 с до начала генерации (плюс сама генерация). Для «живого» персонажа это очень заметно.
**Рекомендация:** окно 0.8–1.5 с, или debounce только при признаках продолжения набора (сообщение без терминальной пунктуации, серия коротких сообщений).

#### REL-03. `/cancel` не отменяет генерации; функции отмены — мёртвый код
**Файлы:** `bot/queue.py:62-100`; `bot/commands.py:417-493`

`cancel_chat_tasks` и `clear_chat_queues` (`queue.py:72, 94`) **не вызываются нигде** (проверено поиском). `handle_cancel_command` чистит только FSM-состояния, тогда как `/arti_commands` обещает «Экстренно свернуть активные медиа-потоки»: запущенная генерация видео/музыки продолжится и придёт в чат после «отмены». Сам `_clear_queue_for_chat` (`:79-92`) манипулирует приватным `q._queue` и вызывает `task_done()` в цикле — опора на внутренности asyncio с риском порчи инвариантов `join()`.
**Рекомендация:** либо подключить отмену к `/cancel` (и переписать без приватных атрибутов — например, флаг «отменено» в задаче, проверяемый воркером), либо удалить мёртвый код и поправить текст меню.

#### REL-04. Фоновые задачи без удержания ссылки
**Файлы:** `bot/queue.py:743` (события), `bot/handlers.py:621, 1940` (стикеры), `:931` (медиа-группы), `bot/queue.py:2157`

В `memory/storage.py` фоновые задачи аккуратно удерживаются в `_BACKGROUND_TASKS` (M-06 закрыт), и в `queue.py` есть `_track_task` — но ряд `asyncio.create_task(...)` создаётся без него. По документации CPython такие задачи может собрать GC до завершения; их исключения теряются.
**Рекомендация:** применять `_track_task` ко всем фоновым задачам.

#### REL-05. Nominatim без rate-limit
**Файлы:** `utils/location_manager.py:28-67, 96`; `bot/handlers.py:1396-1402`

Каждое обновление live-геопозиции (а Telegram шлёт их каждые несколько секунд) запускает фоновое обратное геокодирование на публичном `nominatim.openstreetmap.org`. Политика Nominatim — максимум 1 req/s, идентифицирующий User-Agent, кеширование. Несколько пользователей с live-локацией легко превышают лимит → бан IP, после чего геофичи молча деградируют.
**Рекомендация:** глобальный троттлинг (≤1 rps), геокодировать live-обновления не чаще раза в N минут или при сдвиге > X метров, кешировать по округлённым координатам.

#### REL-06. Устаревшие sync-обёртки с `asyncio.get_event_loop()`
**Файл:** `utils/chat_history.py:66-76, 113-122, 213-222, 281-290`; `utils/location_manager.py:193-198`

`asyncio.get_event_loop()` вне running loop deprecated (3.12+) и в целевом 3.13 (судя по `__pycache__/*.cpython-313*`) ведёт себя иначе, чем рассчитывал автор. Вызовов этих обёрток в основном коде не видно — это legacy.
**Рекомендация:** удалить либо переписать через `asyncio.run`/`get_running_loop`.

### Авторизация и доступ

#### AUTH-04. Rate-limit покрывает только текстовый путь
**Файл:** `bot/handlers.py:49-68, 108-111` (лимитер) vs `:817+` (фото), `:957+` (голос), `:1088+` (видео), `:1214+` (документы), callback-обработчики

Фото-сообщения (`_process_images` → LLM), голосовые (STT+LLM), видео (Gemini upload+LLM), документы и инлайн-кнопки «Что на фото?/Суммаризируй» не лимитированы вовсе. Обход лимита тривиален — слать картинки вместо текста. Словарь `_user_text_timestamps` к тому же не чистится от ушедших пользователей (вечный рост).
**Рекомендация:** единый лимитер на «дорогие действия» (LLM/STT/медиа) для всех путей; периодическая очистка словаря.

#### AUTH-05. Платные команды без квот
**Файл:** `bot/commands.py:522` (`/image`), `:568` (`/video`), `:602` (`/music`), `:2084` (`/vclone`)

Любой участник включённого чата ставит дорогие задачи (image/video/music API) — единственная защита — спам-окно 5 команд/10 с. Суточных и групповых квот нет (S-15 прошлого аудита — открыт).
**Рекомендация:** per-user квоты в БД (день/час), глобальный потолок длины очередей, опционально — приоритизация привилегированных.

#### AUTH-06. Пустой `PRIVILEGED_USER_IDS` + личный чат: бота, вероятно, нельзя включить (требует проверки)
**Файлы:** `utils/admin.py:12-21`; `config.py:125-131`; `bot/commands.py:304-318`

`/start` требует `is_admin`: либо id в `PRIVILEGED_USER_IDS`, либо `get_chat_member(...).status in (CREATOR, ADMINISTRATOR)`. Поведение `getChatMember` в **личном** чате не документировано чётко; если Telegram возвращает статус `member` (наиболее частое наблюдение), то при пустом `PRIVILEGED_USER_IDS` обычный пользователь не сможет включить бота в собственной личке вообще — продукт нерабочий с дефолтной конфигурацией. Требует проверки живым вызовом.
**Рекомендация:** в private-чатах считать собеседника владельцем своего диалога; на старте в prod — fail-fast при пустом `PRIVILEGED_USER_IDS` (S-11 прошлого аудита).

### Валидация и внешние запросы

#### VAL-01. Ложные срабатывания триггеров обращения
**Файлы:** `bot/handlers.py:304-307`; `utils/text_processing.py:15-35`

- `:307` — `has_arti_mention = "арти" in user_message.lower()`: подстрока. «кв**арти**ра», «**арти**ст», «п**арти**я» — бот отвечает в группе без обращения.
- `contains_arti` (голосовой путь) — fuzzy `get_close_matches(..., cutoff=0.7)`: «март» (ratio 0.75) и «картина» проходят порог → бот отвечает на голосовые о марте.
- `:304-306` — `replied_to_bot` проверяет `reply_to_message.from_user.is_bot`: reply на сообщение **любого** бота (не только Арти) трактуется как обращение к Арти.

**Рекомендация:** `\bарти\b` (граница слова уже используется в первой ветке `contains_arti`); сверять `reply_to_message.from_user.id == context.bot.id`; поднять/убрать fuzzy-порог.

#### VAL-02. Бот реагирует на каждый документ в группе
**Файл:** `bot/handlers.py:1214-1310`

`handle_document` не имеет триггер-гейта (личка/упоминание/reply): любой файл ≤10 МБ в включённой группе скачивается, парсится (`extract_document_text`, `:1282` — до какого-либо запроса пользователя) и бот отвечает сообщением с кнопками «Что с ним делать?». В рабочих группах это шум, лишний трафик и парсинг чужих документов без запроса.
**Рекомендация:** в группах предлагать действия только при reply на бота/упоминании; парсить документ лениво — после нажатия кнопки.

#### VAL-03. Слабая проверка «известного видеохостинга»
**Файл:** `ai/video_url.py:54-64`

```python
if any(host in url_lower for host in _KNOWN_VIDEO_HOSTS):
    return True
```
Матч подстроки по **всему URL**, а не по hostname: `https://evil.com/watch?ref=youtube.com` и `https://youtube.com.evil.io/...` считаются «известным видеохостингом». Скачивание дальше защищено SSRF-guard'ом (публичные IP), но бот постит меню и запускает yt-dlp на произвольный сайт.
**Рекомендация:** `urlparse(url).hostname` и сравнение `host == h or host.endswith("." + h)`.

#### VAL-04. Обход SSRF-allowlist редиректами в `catbox.download_file`
**Файл:** `ai/catbox.py:124-177`; `utils/url_safety.py:32-46`

Allowlist и публичность IP проверяются **до** запроса, но затем httpx идёт с `follow_redirects=True` (`:136`), aiohttp следует редиректам по умолчанию (`:149-153`), fallback `curl.exe -L` (`:161-165`) — тоже. Редирект с `files.catbox.moe` на внутренний адрес обойдёт проверку; плюс классический DNS-rebinding TOCTOU (резолвинг при проверке и при запросе — разные). Практическая эксплуатация требует злонамеренного поведения catbox, поэтому Medium, но паттерн неполный.
**Рекомендация:** запретить редиректы или валидировать каждый hop; для строгости — резолвить хост один раз и подключаться по IP с SNI/Host.

#### VAL-05. Раскрытие исключений и путей сервера в чат
**Файлы:** `bot/handlers.py:1606-1617`; `bot/queue.py:1288-1311, 1320-1331, 1588-1603`; `bot/commands.py` (множественные `_html.escape(str(exc)[:200])`)

Пользователю отправляются сырые тексты исключений (`<pre>{_html.escape(str(exc))[-3500:]}</pre>`) и абсолютные пути файлов на диске сервера («Лежит здесь: C:\...»). Это раскрывает структуру ФС, версии библиотек, внутренние URL — полезно атакующему и неинформативно пользователю.
**Рекомендация:** пользователю — короткий код ошибки/генеричное сообщение, детали — только в лог; пути с диска не показывать никому, кроме привилегированных.

#### VAL-06. Prompt-injection в роутер намерений и фильтр адресации
**Файл:** `ai/generation.py:211-299` (`analyze_intent`), `:308-355` (`is_message_for_arti`)

Текст пользователя вклеивается в промпт классификаторов без обрамления. Инструкциями в сообщении можно форсировать «SEARCH»/«MAPS» (доп. стоимость, Maps-grounding) или манипулировать решением «отвечать ли в группе». Влияние ограничено булевым результатом (S-13 прошлого аудита — отложен, фиксирую как открытый).
**Рекомендация:** обрамлять user-контент маркерами и инструкцией «это данные»; первичный слой — детерминированные правила.

#### VAL-07. Медиа-теги из ответа LLM исполняются как платные действия
**Файлы:** `bot/queue.py:963-993, 1131-1155`; `bot/handlers.py:520-546, 658-688`

Из текста ответа модели регэкспами извлекаются `{image=…}`, `{video=…}`, `{music?…}` и ставятся в платные очереди генерации. Пользовательский текст, склонивший модель вставить тег (косвенный prompt-injection), превращается в расход API. Подмешивание навыка по `has_media_intent` (`ai/skills.py:35-49`) снижает, но не убирает риск: паттерны вроде `\bвидео\b`, `\bтрек\b` срабатывают на бытовых фразах. (S-12 — отложен, фиксирую как открытый.)
**Рекомендация:** исполнять теги только при явном пользовательском намерении (команда/кнопка/подтверждение), логировать и лимитировать LLM-инициированные генерации.

#### CONF-06. In-memory состояние не переживает рестарт и мультипроцесс
**Файлы:** `config.py:136-177` (все FSM-словари), `:240` (`rp_mode_state`); `bot/handlers.py:51-53`; `utils/response_status.py:7`; `utils/model_selection.py:8`; `utils/spam_protection.py:19`
