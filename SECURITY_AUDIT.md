## Часть I. Ошибки и риски в модуле памяти

Разобраны: `memory/storage.py`, `memory/extractor.py`, `memory/consolidator.py`, `memory/profiles.py`, `memory/timeline.py`, `memory/chunking.py`, `memory/embeddings.py`, `memory/normalizer.py` и связанные методы `database/models.py`.

### M-01 (High). Неверная привязка фактов к сущностям через подстроку
**Файл:** `memory/storage.py`, строка 328

```328:328:memory/storage.py
        linked_entity_ids = [entity_id for normalized, entity_id in entity_by_name.items() if normalized in normalize_entity_name(text)]
```

**Проблема:** связь факта с сущностью определяется проверкой «нормализованное имя сущности входит как подстрока в текст факта». Короткие имена (например, `ян`, `ал`, `кот`) будут ложно срабатывать внутри других слов («**ян**варь», «к**ал**ендарь», «**кот**ёнок»). Это засоряет граф знаний ложными рёбрами `fact↔entity`, что напрямую влияет на ранжирование в `MemoryFact.search` (через `entity_boost`).

**Исправление:** сопоставлять по границам слов (токенизация + точное сравнение нормализованных токенов) либо хранить уже извлечённые сущности факта, а не угадывать по подстроке.

### M-02 (High). Рассинхрон размерности эмбеддингов с моделью
**Файл:** `memory/embeddings.py`, строки 12-13

```12:13:memory/embeddings.py
EMBEDDING_MODEL = "gemini-embedding-2"
EMBEDDING_DIMENSIONS = 1536
```

**Проблема:** размерность `1536` зашита и в коде, и в схеме (`embedding vector(1536)` в `database/connection.py:494`). Если модель эмбеддингов вернёт вектор иной длины (смена модели/версии API), вставка в `pgvector` упадёт с ошибкой размерности, а в `set_embedding` ошибка не перехватывается отдельно — чанк останется без эмбеддинга, и поиск молча деградирует до текстового. Нет проверки `len(vector) == EMBEDDING_DIMENSIONS` перед записью.

**Исправление:** валидировать длину вектора перед `set_embedding`; при несоответствии логировать и пропускать; хранить размерность в конфиге согласованно со схемой и проверять на старте.


### M-04 (Medium). Bypass cooldown делает «остывание» фактов почти бесполезным
**Файл:** `database/models.py`, строки 949-956

```949:956:database/models.py
                WHERE (
                    cooldown_until IS NULL 
                    OR cooldown_until < NOW()
                    -- Bypass cooldown if FTS rank is exceptionally high (e.g. > 0.1) OR it is an exact text substring match
                    OR rank > 0.1
                    OR is_direct_match
                )
```

**Проблема:** `mark_used` ставит `cooldown_until` на час вперёд (строка 994), чтобы один и тот же факт не повторялся в каждом ответе. Но в поиске cooldown обходится, если `rank > 0.1` **или** факт — прямое подстрочное совпадение. Для релевантных запросов это почти всегда true, поэтому механизм cooldown фактически не работает именно тогда, когда он нужен — бот будет навязчиво повторять один и тот же факт.

**Исправление:** пересмотреть логику — например, мягко понижать вес недавно использованных фактов (`used_count`/recency penalty уже частично есть в `ORDER BY`), а не полностью обходить cooldown.

### M-05 (Medium). Wiki-предложения сохраняются даже при пустом плане архивации
**Файл:** `memory/consolidator.py`, строки 204-222

```204:222:memory/consolidator.py
    # 1. Сохраняем новые Wiki-предложения как не верифицированные
    suggested_wiki_ids = []
    for sug in plan["wiki_suggestions"]:
        page_id = await MemoryWikiPage.save(...)
        if page_id:
            suggested_wiki_ids.append(page_id)
    report["suggested_wiki_ids"] = suggested_wiki_ids

    if not plan["archive_ids"]:
        return report
```

**Проблема:** wiki-страницы записываются в БД до проверки `archive_ids`. При непустых `wiki_suggestions`, но пустом `archive_ids`, функция сохранит вики и выйдет, **не создав консолидированные факты** (`plan["facts"]`). Операция не атомарна: при ошибке между сохранением вики и созданием фактов состояние памяти окажется частичным. `MemoryWikiPage.save` использует upsert по `(mode, page_key)`, поэтому LLM-предложение может перетереть уже существующую (в т.ч. верифицированную вручную) страницу с тем же `page_key`, сбросив `is_verified` в `False`.

**Исправление:** обернуть применение плана в одну транзакцию; не перезаписывать `is_verified=True` страницы предложениями; разделять `page_key` LLM-предложений (префикс/namespace).

### M-06 (Medium). Утечка fire-and-forget задач консолидации/профиля
**Файл:** `memory/storage.py`, строки 369-415

**Проблема:** `remember_exchange` создаёт фоновые `asyncio.create_task` для консолидации и перестроения профиля. Ссылка на задачу — локальная переменная; хотя добавлен `add_done_callback` для логирования ошибок, ссылка не удерживается в долгоживущем контейнере. По документации CPython такие задачи могут быть собраны GC до завершения. Кроме того, нет ограничения на число одновременных фоновых LLM-задач — при всплеске трафика это неконтролируемая нагрузка на API и БД.

**Исправление:** хранить задачи в модульном `set()` и снимать в callback; ограничить параллелизм семафором.

### M-07 (Medium). Смешение `datetime.now()` (naive) и времени БД (`NOW()`)
**Файлы:** `database/models.py` — `mark_used` (строки 999-1007), аффективные методы (1176-1201, 1259-1274)

**Проблема:** `cooldown_until` вычисляется как `datetime.now() + timedelta(...)` (наивное локальное время приложения) и сравнивается в SQL с `NOW()` (время сервера БД). Если приложение и БД в разных таймзонах/часовых поясах, окно cooldown окажется смещённым (слишком коротким или длинным). Аналогично аффективные кулдауны (`last_reinforcement_time`, `last_passive_growth_time`) используют `datetime.now().isoformat()` без таймзоны. В `update_state` это уже исправлено правильно (дельта считается на стороне БД, см. комментарий в `models.py:1705-1710`), но в остальных местах — нет.

**Исправление:** везде вычислять временные окна на стороне БД (`NOW() + interval`) или использовать `datetime.now(timezone.utc)` согласованно.

### M-08 (Medium). `find_mentions` / `find_related`: подстрочный матчинг ILIKE по сущностям
**Файл:** `database/models.py`, строки 691-711 (и аналогично 668-688, 858-869)

```702:707:database/models.py
                AND (
                    $2 ILIKE '%' || e.normalized_name || '%'
                    OR e.normalized_name ILIKE '%' || $2 || '%'
                    OR $2 ILIKE '%' || a.normalized_alias || '%'
                    OR a.normalized_alias ILIKE '%' || $2 || '%'
                )
```

**Проблема:** двунаправленный `ILIKE '%...%'` по всему тексту сообщения. Короткие имена/алиасы дают массу ложных срабатываний (та же природа, что и M-01). Кроме того, текст пользователя подставляется в `ILIKE`-паттерн без экранирования `%` и `_` — спецсимволы LIKE в имени сущности или в сообщении исказят матчинг (не инъекция, т.к. параметризовано, но логически неверно). При больших таблицах двунаправленный leading-wildcard `ILIKE` не использует индексы и приводит к seq scan.

**Исправление:** матчинг по нормализованным токенам/границам слов; экранировать LIKE-метасимволы; для масштабирования — триграммный индекс (`pg_trgm`).

### M-09 (Low). `dominant_mood` при пустом/нулевом `mood_state`
**Файл:** `memory/storage.py`, строки 116-121

```116:121:memory/storage.py
        dominant_mood = "thinking"
        max_val = -1.0
        for emotion, val in mood_dict.items():
```

**Проблема:** если все настроения равны `0.0` (свежесозданное состояние), `max_val` станет `0.0`, а `dominant_mood` — первая эмоция словаря (`happy`), а не «нейтральное» `thinking`. **Исправление:** трактовать `max_val <= 0` как отсутствие выраженной эмоции и оставлять нейтральный дефолт.

### M-11 (Low). `_fallback` экстрактора может сохранять «мусорные» факты
**Файл:** `memory/extractor.py`, строки 42-51

**Проблема:** при ошибке/невалидном JSON от LLM `_fallback` сохраняет склейку «Пользователь: ... Арти: ...» как факт с `importance=0.35`, если длина ≥ 80 символов. Это сохраняет сырой диалог (включая одноразовые эмоции и шум, которые системный промпт явно просил не сохранять) как «факт». Со временем засоряет память и консолидацию.

**Исправление:** в fallback сохранять только summary без создания factoid, либо помечать такие записи спец-метаданными и исключать из выдачи/консолидации.

### M-12 (Low). `keyword_query` отбрасывает значимые короткие слова
**Файл:** `memory/normalizer.py`, строки 3, 22-33

### High

#### S-04. SSRF через `catbox.download_file`
**Файл:** `ai/catbox.py`, строки 120-155
Пользовательский URL (например, из `/voice_save`) скачивается без проверки → запросы к `127.0.0.1`, cloud metadata, внутренним сервисам; `follow_redirects=True` и fallback на `curl.exe -L` усиливают обход.
**Исправление:** allowlist хостов (`files.catbox.moe`, `litter.catbox.moe`), блокировка private/link-local IP, запрет редиректов на внутренние адреса.

#### S-05. SSRF через yt-dlp (видео/аудио по URL)
**Файлы:** `ai/video_url.py` (67-93), `ai/dubbing.py` (88-96), `bot/commands.py` (2192-2196, vclone по любому `http(s)://`).
Запросы к внутренним сервисам/metadata-эндпоинтам, тяжёлая нагрузка.
**Исправление:** allowlist доменов, блок private IP, egress-фильтр/прокси, изолированный worker.

#### S-06. Обход проверки admin для `/dub`
**Файлы:** `bot/handlers.py` (1768-1796, `vurl:dub`), `bot/commands.py` (1391-1395 — admin-проверка только в `handle_dub_command`).
Любой пользователь в ЛС запускает тяжёлый videotrans-pipeline через callback, минуя ограничение «только админы».
**Исправление:** вызывать `is_admin()` в `video_url_action_callback` и перед `_enqueue_dub_task`.

#### S-07. IDOR при удалении воспоминаний (`/forget`)
**Файлы:** `database/models.py` (`MemoryFact.search` 837-958 — фильтр по `chat_id` без `user_id`; `archive_many` 977-990 — только по `fact_id`), `bot/commands.py` (`forget_callback` 3756-3762).
В групповом чате участник может видеть и удалять факты других пользователей того же `chat_id`.
**Исправление:** фильтровать по `user_id`; в `archive_many`/`forget_callback` проверять принадлежность факта (`chat_id`, `user_id`) или право модератора.

#### S-08. SSRF через `requests.get` по URL от внешних API
**Файлы:** `bot/queue.py` (234-247), `ai/image.py` (357-376).
Скомпрометированный/злонамеренный ответ внешнего API → fetch произвольного URL с сервера бота.
**Исправление:** применять `_is_safe_image_url()` / общий SSRF-guard перед любым `requests.get`.
